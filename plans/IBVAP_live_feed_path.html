IBVAP Live Feed Path

Real video, synthetic sources, and the three channels that keep them apart.

The edge node already judges detections it is handed. This paper covers the layer beneath it: where the frames come from, who decodes them, and how video reaches the operator's screen without the detector ever standing between the two. Nothing above the ingress hook changes.

Topology

Four processes, one box

Everything below runs on a single machine at the post. The separation is about failure isolation and language boundaries, not about distribution — there is still no cloud service anywhere in the working path.

The load-bearing decision: the backend is not in the video path. Video goes from the media hub to the browser directly. Detection load can spike, the vision worker can crash and restart, the edge node can be redeployed — and the operator's picture never stutters, because none of those processes are carrying frames to the screen.

The vision service and the edge node are the two halves you described as one backend. They stay separate processes because they are different languages, restart on different cadences, and one of them is allowed to die at any moment while the other holds the record.

The central idea

Three channels, deliberately unmuxed

Video, boxes, and the record travel separately because they have nothing in common except a destination. Different rates, different durability, different consequences when they break.

Muxing boxes into the video server-side — burning them into the frames — couples the three together at the worst possible point: it puts the detector in the video path, forces re-encode on every camera, and means a slow model produces stuttering video rather than late boxes. Keep them apart and a slow model produces exactly one symptom: slightly late boxes.

Read the last row as the design justification. Three independent failure modes, none of which takes the others down, is what the split buys you.

Why boxes are never stored

At 8 fps across four cameras with three subjects in view, the box channel is roughly a hundred detections a second. Writing those anywhere durable would dwarf the event log by four orders of magnitude and destroy the property that makes the current design work — that the database stays small enough to live at a remote post.

The boxes exist for exactly one purpose: drawing a rectangle on a screen someone is looking at right now. The moment nobody is watching, they are worthless. What survives is what the fence decided about them — and that is already modelled, already durable, and already only a few rows per minute.

Sequencing advantage

IBVAP's evidence is geometry, not frames. The incident review overlay replays a walked path against a zone shape — it needs no video at all and no clock alignment. So live video and box-overlay precision are separable milestones. You can ship a live tile with zone outlines and no boxes at all, and the forensic path is untouched.

v0 sources

Clips on a loop, indistinguishable downstream

No cameras yet, so the media hub gets fed by ffmpeg reading video files in a loop. The point is not that it is easy — it is that it enters at the same place a camera will, so nothing downstream can tell the difference.

This is the same move the repo already makes one layer up. src/sim/simulator.ts posts through ingestDetections, the identical function the HTTP hook calls, so the fence cannot tell a simulated walker from a real one. The clip loop does that for the media layer: MediaMTX publishes a path called cam_fence_north, and whether that path is fed by ffmpeg or by a camera on the wall is invisible to every reader.

mediamtx.yml — v0, synthetic
paths:
  cam_fence_north:
    # -re     read at native frame rate, or ffmpeg blasts the whole
    #         file through in seconds and the "camera" runs at 400×
    # -c:v copy  no transcode; requires the clip to already be H.264
    runOnInit: >
      ffmpeg -re -stream_loop -1 -i /clips/fence_north.mp4
             -c:v copy -an -f rtsp
             rtsp://127.0.0.1:$RTSP_PORT/$MTX_PATH
    runOnInitRestart: yes

  cam_farm_gate:
    runOnInit: >
      ffmpeg -re -stream_loop -1 -i /clips/farm_gate.mp4
             -c:v copy -an -f rtsp
             rtsp://127.0.0.1:$RTSP_PORT/$MTX_PATH
    runOnInitRestart: yes
mediamtx.yml — the day a camera arrives
paths:
  cam_fence_north:
    source: rtsp://admin:••••@10.0.0.14:554/Streaming/Channels/102
    # channel 102 = substream. 101 would be the main stream.

That is the entire migration. One block of config per camera, the path name unchanged, the ffmpeg processes deleted. The vision service still pulls rtsp://127.0.0.1:8554/cam_fence_north; the browser still asks for the same WHEP endpoint; the seeded camera.id rows in SQLite still line up.

Choosing the clips

The clips are test fixtures and should be picked like fixtures — each one should make a specific behaviour observable. The scenario list in src/sim/simulator.ts is already the right inventory, and the negatives matter more than the positives: footage of cattle crossing a fence line proves the log-only routing works; a person stepping over and straight back proves flicker rejection works. Those are harder to demonstrate and more convincing than an intruder walking through.

Pin the codec

Encode the clips as H.264, not H.265. WebRTC in most browsers will not accept HEVC, so an H.265 source forces MediaMTX to transcode every stream — spending exactly the CPU you wanted for inference. The same trap waits on real hardware, where plenty of modern IP cameras ship H.265 by default and have to be reconfigured.

The two halves

What each side owns

You described the backend as two submodules — one doing detection and analysis, one storing actions. That is the right cut. Here is where the line falls.

The asymmetry in the "may crash" row is the reason to keep them as separate processes rather than one. The vision service is doing the risky work — decoding untrusted streams, running a model, managing GPU or thread pools. It should be disposable. The edge node is doing the work that must not be lost, and it should be the boring process that stays up for weeks.

The seam already exists

Nothing in src/l2, src/l3 or src/l4 changes. The vision service POSTs to /hooks/ingress/detections — the endpoint the README already describes as the one a real detector will point at. The simulator stays exactly where it is, because it is still the only way to reproduce a flicker on demand.

Keep the simulator

When real feeds land, do not delete src/sim/simulator.ts. It becomes the test harness and the offline demo mode, and it costs nothing to keep because it goes through the same door as everything else. A clip loop gives you repeatable footage; the simulator gives you repeatable geometry, which is what the fence tests actually assert on.

Message shapes

Two payloads, one bbox convention

The single most important thing to settle before any code is written: there is one bounding-box convention, and it is the one already in the codebase.

Do not introduce a second convention

The sketch payload used [x1, y1, x2, y2] in absolute pixels. The existing Detection type in src/core/types.ts uses [x, y, w, h] normalised 0..1, and the entire zone system depends on normalisation — it is what lets a zone survive a camera swap, and what lets detection run on a 640×360 substream while display runs at 1080p.

Two conventions in one system is a bug factory: every boundary becomes a place where someone forgets to convert, and the failure is silent because a wrong box still looks like a box. Pick [x, y, w, h] normalised, everywhere, both channels.

What the box channel deliberately does not carry

No zone state, no severity, no incident id. The vision service does not know what a zone is and should not learn — that knowledge lives one layer up, and pushing it down would put force-specific configuration into the pixel pipeline.

So the live overlay is composed from three sources rather than one: neutral boxes from the WS, static zone outlines from /api/config, and a flash on the zone when an event arrives over SSE. That is also why the two frontend channels stay separate rather than being merged into one socket — they come from different processes and mean different things.

Prerequisites

Four things in the current code that real feeds break

All four are invisible today because the simulator is well-behaved: it never recycles a track id, it shares a clock with the backend, and it runs at 4 fps. A real detector is none of those things.

01
Track ids get recycled

Real trackers — ByteTrack, BoT-SORT, DeepSORT — reuse integer ids once a track dies, and reset to 1 on worker restart. Two different people will land on the same row, and the second will inherit the first's zone-crossing state, including a pending crossing waiting to confirm.

where  fence.ts:58 trackKey · schema.sql:148 UNIQUE(camera_id, track_ref)

fix  Namespace the ref with a per-run id from the vision service — r7c2:14 rather than 14. Cheap, and it makes worker restarts safe by construction.

02
Wait-and-confirm runs on wall-clock arithmetic

The confirm state machine measures held time by differencing parsed timestamps. On a post with no NTP, a clock step makes a pending crossing either confirm instantly or never confirm at all — and the whole point of the seconds-not-frames design was that the setting means the same thing everywhere.

where  fence.ts:347 Date.parse(frame.occurred_at) / 1000

fix  Carry capture_mono on the frame and use it for the confirm maths. Wall clock stays for occurred_at, storage and display only.

03
A SQLite write per detection per frame

upsertTrack re-serialises the whole path to JSON and UPDATEs on every detection of every frame. At four cameras × 8 fps × three subjects that is around a hundred writes a second. The interesting part: nothing reads that column — evidence.path is built from the in-memory track.path at emit time, so the write is very nearly pure cost.

where  fence.ts:103 UPDATE tracked_thing SET last_seen …

fix  Drop the per-frame write, or batch it on an interval. Persist the path once at emit time, where it is actually read.

04
Camera credentials would leak through /api/config

RTSP URLs embed credentials — rtsp://admin:password@10.0.0.14/…. The camera.stream_url column exists and is unused; populating it with a real URL hands camera passwords to every browser that loads the console, and there is no auth on that route.

where  schema.sql:37 stream_url · server.ts /api/config

fix  The frontend receives a hub path name only. The real URL lives in the MediaMTX config, server-side, and never enters SQLite or an API response.

Worth doing now

Fixes 01 and 02 are cheap while the simulator is the only producer and expensive once a real tracker is attached — they change the shape of data crossing the ingress hook. Do them before wiring the vision service, not after.

Decisions

Open calls, with a recommendation each

Transportboxes
Rec — WebSocket
WS or a second SSE stream?

SSE would work and the infrastructure exists. WS earns its place on one thing only: the client can talk back, so a console showing one tile fullscreen can unsubscribe from the other seven cameras' boxes.

At four cameras that saving is nothing. At sixteen it is the difference between a usable console and a busy one. Take WS now because retrofitting subscription control later means changing both ends.

Routingboxes
Rec — direct from vision
Boxes via the edge node, or straight to the browser?

Routing through the edge node gives the frontend a single origin and one CORS config. But it puts a hundred messages a second through the process that owns the audit chain, for no benefit — the edge node has nothing to add to a raw box.

Direct from the vision service keeps per-frame traffic entirely out of the durable-record process, and gives you the failure isolation in Plate B.

Syncoverlay
Rec — best-effort in v0
How closely must boxes track the video?

WebRTC frame timestamps and detection timestamps live in different clocks, and reconciling them properly means a detection ring buffer keyed on capture time plus requestVideoFrameCallback.

For v0, draw the latest box set for each camera over the current frame. Sub-100ms misalignment on a walking person is invisible. Revisit only if someone actually complains — and remember the forensic overlay never had this problem at all.

Rateinference
Measured — one machine
How fast does detection actually run?

An earlier draft of this paper recommended a figure here. It should not have: claude.md §7 forbids quoting a rate nobody measured, and against the Ryzen 3 floor a guess is worse than useless.

One camera, imgsz=480, detect_every=2, synthetic clip, 2026-09-06: 20.8 fps pipeline, 66.1 ms per detector call. One machine, and an empty scene — a frame with people in it costs more, and four workers on one box divide these cores between them. Re-measure per laptop with service.py --seconds 30.

Still needed from you

  • Edge hardware — CPU-only x86, or Jetson / discrete GPU? Sets how many streams decode in parallel and whether 8 fps across four cameras is comfortable or marginal.
  • Model choice — this paper assumes a single-stage detector plus a lightweight tracker, which is what ibvap/core/person.py implies. Worth confirming before the fps budget above means anything.
  • Console location — same LAN as the edge box, always? If the console might ever run off-site, WebRTC needs STUN/TURN and the topology grows a hop.
  • Tile count — how many cameras visible at once on one screen? Four tiles of WHEP is unremarkable; sixteen needs thought about decode load in the browser.

Operations

What each process taking down looks like

The schema already models a blindness ladder — FULL · DEGRADED · MOTION_ONLY · RECORD_ONLY · DEAD on the camera row — which is currently decorative because nothing produces the signal. Real streams produce it.

DiesOperator seesStill workingDrives status to
ffmpeg clip loop One tile goes black Everything else, including other cameras DEAD
MediaMTX All tiles black, no detections Console, history, audit — the record is intact DEAD (all)
vision service Video keeps playing. Boxes freeze. Video, console, history, audit DEGRADED
edge node Console stale; no new incidents Video, boxes — the picture is still live RECORD_ONLY
inference falls behind Boxes lag visibly, then thin out Everything, at reduced detection rate MOTION_ONLY
browser reloads Momentary blank, then recovery All three channels reconnect — no change

Two rows are worth dwelling on. The vision service dying leaves the picture live — an operator can still watch the fence with their own eyes while the detector restarts, which is a meaningfully better failure than a black screen. And the browser reload row is free: WHEP renegotiates, the WS reconnects, and the SSE stream replays missed events via ?after_seq=, which the event table's monotonic seq was built for.

The supervisor's real job

Not much, in v0. MediaMTX's runOnInitRestart handles the clip loops itself, so the supervisor reduces to a camera manifest plus whatever restarts the vision service — systemd, a compose file, or a twenty-line Python parent. The interesting work is the column above: turning process liveness into the camera.status the operator screen already knows how to display.

Sequencing

Build order

Ordered so that each milestone is demonstrable on its own and nothing is built against an interface that has not been proven yet.

  1. Fix the two shape-changing prerequisites

    Run-scoped track_ref and capture_mono on the ingress frame. Update the simulator to emit both — it is the cheapest place to prove the new shape works, and the fence tests will catch anything that moves.

  2. MediaMTX with clip loops, nothing consuming it

    Four paths, four looping clips, verified with ffplay rtsp://…. No code written yet. Confirms codec, frame rate, and that -c:v copy holds.

  3. Video in the browser, no boxes

    One WHEP tile in the console with the zone outlines drawn over it from /api/config. This is already a real demo — live video with the virtual fence visible on it — and it needs no detector at all.

  4. Vision service → ingress hook

    Python worker pulls RTSP, detects, tracks, POSTs frames. The console's existing incident list starts filling from real footage. The seam is already built for this.

  5. Box channel over WS

    Add the WS server to the vision service, the canvas overlay to the tile. Best-effort sync. This is the last piece and the most visible one, which is exactly why it goes last.

  6. Health signal → camera.status

    Wire stream and worker liveness into the blindness ladder, so the console can say out loud where it is blind rather than failing quietly.

Note on M3

Milestone 3 is worth calling out separately: live video with zone outlines and no detection is a complete, showable artefact that depends on none of the hard parts. If a demo is coming before the model is ready, that is the thing to have working.

Scope

Deliberately not in v0

Written down so they are decisions rather than omissions. Each one is a thing the architecture leaves room for and does not build.

Auth
No real logins

The x-ibvap-actor header stays. The property that matters — no write path is anonymous — already holds, and it is the part that would be expensive to add later.

Storage
No video recording

Evidence stays geometry. Adding continuous recording is a MediaMTX config change, but it makes a retention sweeper urgent, and disk is where video goes to eat a post alive.

Sync
No frame-accurate overlay

Best-effort boxes. The forensic path never needed alignment, so this only ever affects the live tile.

Vision
No cross-camera re-ID

The same_as column exists and stays empty. Real appearance features are a v2 problem and a much heavier model.

Network
No STUN/TURN

Console and edge box on the same LAN. Off-site viewing changes the topology and is worth pricing separately.

Distribution
No post-to-HQ sync

Still one box. ?after_seq= is already the right primitive when it comes, which is why it exists now.
