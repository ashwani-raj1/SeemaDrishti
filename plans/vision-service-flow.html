IBVAP Vision Service Flow

One process. Two threads plus three per camera. Video goes in; the same detections leave down two channels that agree on nothing except their contents — one hot and disposable, one cold and durable. Nothing in here knows what a zone, a severity or an incident is.

FIG 01What runs, and where the boxes go

The whole process at rest. Every arrow crosses a thread boundary, which is why each one is either a queue or a thread-safe hand-off — never a plain call.

Thread count is 2 + 3N. Four cameras on one laptop is 14 threads — before torch spawns its own intra-op pool, which this diagram does not draw and which is a real part of why workers on one box starve each other. That is the whole reason IBVAP_WORKER_CAMERAS exists.

FIG 02Where the config comes from

Two files, two questions, never merged. Every laptop reads the same manifest and a different IBVAP_WORKER_CAMERAS — that split is what makes one-worker-per-machine work.

FIG 03The per-frame loop

One camera’s worker thread, from frame to both channels and back. This is where the CPU budget is actually spent — and where two early exits stop work before it starts.

Read the two early exits as the CPU budget. At detect_every=2, half the decoded frames die at the second diamond having cost only a decode. The detector — the one heavy box on this page — runs on what is left. Everything below it is microseconds.

FIG 04Why the reader drops frames

cv2.VideoCapture.read() pulls sequentially from an internal buffer. If inference is slower than the stream, that buffer grows and a “live” feed silently goes stale — the failure that collapses demos on stage.

FIG 05Shutdown

Three things end a run: Ctrl-C, every worker dying, or the --seconds deadline. All three land in the same path.

  1. Signal or deadline sets stopping SIGINT and SIGTERM both only set an event — no work happens inside the handler. SIGTERM is wrapped in a try, because not every Windows console host has it.
  2. worker.stop() sets _halt Named _halt, not _stop: Thread uses that name internally, and shadowing it breaks join() with a confusing TypeError.
  3. join(timeout=5.0) per worker The loop checks _halt once per frame, so a worker exits within roughly one detector call.
  4. Each worker’s finally block closes its own two children reader.stop() then ingress.stop(). Ownership stays local — the main thread never reaches into a worker’s threads.
  5. print_report() One row per camera. These are the only performance figures anyone on the team may quote.
  6. boxes.stop() last Sets an asyncio Event rather than stopping the loop, so async with serve(...) unwinds normally instead of trying to schedule its own close on a loop that is already gone.
